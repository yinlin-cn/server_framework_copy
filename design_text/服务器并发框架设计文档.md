# 服务器并发框架设计文档

> 面向课程设计 / 对外展示的最终架构说明，不包含开发过程复盘。
> 配套文件：`服务器并发框架.drawio`（架构图）、根目录 `README.md`（使用手册）、`aggregation/tools/PRESSURE_TEST.md`（压测报告）。
>
> 代码版本：v0.9（含多 Reactor 双 epoll、低水位 Reactor 重试、协程挂起屏障、发送队列上限）

---

## 1. 系统概述

本系统是一个基于 Linux `epoll + 线程池 + C++20 协程` 的高并发短任务服务器框架，定位是“一条消息从进入到回复”的完整服务链路。

设计目标：

- 网络收发、协议解析、业务执行、数据库访问分层解耦；
- 业务开发者只接触少量接口，不感知 fd、epoll、Reactor 等底层实现；
- 查询数据库等耗时等待通过协程挂起，业务线程不阻塞；
- 使用有界队列、连接窗口与数据库准入额度实现背压，极端负载下不丢数据；
- 支持优雅退出、错误回调、指标采集、日志记录与连接心跳清理；
- 提供连接名册与框架调用层，支撑单发、组播、分组、主动关闭等通用服务。

非目标：

- 不承载持续运行的长任务（由业务层独立线程承担）；
- 不提供分布式编排、网关、TLS 等生产级平台能力；
- 不在框架层限制查询行数或执行业务规则。

## 2. 总体架构

```text
┌─ 网络 IO 层 ─────────────────────────────────────────────┐
│ Acceptor（epoll + eventfd）                                │
│   → 新连接轮询分配给 N 个 Reactor                         │
│ Reactor = epoll + eventfd + 事件线程 + 连接表              │
│   → 长度头拆包 → 连接窗口准入 → 业务分类 → 投递             │
│   → BatchSender 攒批唤醒 → Reactor 批量发送                │
└───────────────────┬───────────────────────────────────────┘
                    ▼
┌─ 解析线程池（divide_pool）────────────────────────────────┐
│ 消息 → 业务闭包（std::function<void()>）                  │
└───────────────────┬───────────────────────────────────────┘
                    ▼
┌─ 业务工作线程池（work_pool）──────────────────────────────┐
│ 执行闭包；需要等待时协程挂起，线程归还                     │
│ 数据库结果到达后，经阻塞队列取回恢复任务并 resume           │
└───────────────────┬───────────────────────────────────────┘
                    ▼
┌─ 数据库层（DB_pool + connect_pool）───────────────────────┐
│ prepared statement 参数化执行 → 结果写入信箱 → 唤醒业务     │
└───────────────────────────────────────────────────────────┘
```

### 2.1 分层职责

| 层 | 职责 | 核心组件 |
|---|---|---|
| 网络 IO 层 | 接收连接、收发数据、长度头拆包、心跳、连接管理 | `Acceptor`、`Reactor`、`Internalconnection`、`Handler_epoll_make` |
| 批处理层 | 合并 Reactor 唤醒信号，降低系统调用次数 | `BatchSender`、`Handler_batch_make` |
| 解析层 | 消息路由分类，把消息解析成业务闭包 | `divide_pool`、`Handler_divide_make` |
| 业务层 | 执行业务逻辑，协程挂起与恢复 | `work_pool`、`thread_pool`、`EventAwaiter`、`blockingqueue` |
| 数据库层 | 参数化 SQL、结果读取、协程唤醒 | `DB_pool`、`connect_pool`、`Handler_DB_make` |
| 框架调用层 | 连接名册、虚拟连接标识、单发/组播/分组/关闭 | `connect_book`、`FrameworkCall`、`ConnectionSession` |
| 运维层 | 指标采样、日志、错误回调、心跳监控 | `Metrics`、`Logger`、`ErrorHandler` |
| 集成层 | 组装全部组件并控制生命周期 | `Server`、`NetworkServer`、`ReactorControl` |

## 3. 线程模型

| 角色 | 数量 | 职责 |
|---|---|---|
| Acceptor 线程 | 1 | epoll 监听、accept 新连接，轮询分配给 Reactor |
| Reactor 事件线程 | N（默认 4） | 本组连接的读写、心跳、关闭 |
| 解析 worker | 可配置（默认 16） | 把消息解析成业务闭包 |
| 业务 worker | 可配置（默认 20） | 执行业务任务与协程恢复 |
| DB worker | 可配置（默认 50） | 执行 SQL、写信箱、唤醒业务池 |
| BatchSender 线程 | 1 | 周期唤醒“有待发数据”的 Reactor |
| Metrics 采样线程 | 1 | 每秒输出指标快照 |
| Logger 线程 | 1 | 批量写入日志文件 |

线程间通信原则：

- 业务线程发送数据只入队，Reactor 事件线程统一写出；
- Reactor 通知业务层只投递任务；
- 协程完成方（DB worker）不直接 resume，恢复任务回到业务池执行；
- 跨线程唤醒 Reactor 使用 eventfd；
- worker 使用 thread_local 白板保存当前连接。

## 4. 消息完整生命周期

```text
客户端
  │  [4 位十进制 ASCII 长度][UTF-8 消息体]
  ▼
Reactor 读取并拆包
  ├─ 每连接窗口有空位才取消息
  ├─ 分类：fast 直接进入；db 需要 DB 准入额度
  └─ 额度不足 → 等待区，暂停该连接读取
  ▼
divide_pool：消息 → 业务闭包
  ▼
work_pool worker：设置线程白板并执行
  ├─ 纯 fast 业务 → 直接 send 回包
  └─ 需要 DB → co_await query_db
        ├─ 协程挂起，恢复任务进入阻塞队列
        ├─ DB worker 参数化执行 SQL
        ├─ 结果写入信箱，等待业务任务真正返回
        └─ 恢复任务回到 work_pool，业务 worker resume
  ▼
业务发送 reply（BatchSender 攒批唤醒 Reactor）
```

## 5. 关键机制

### 5.1 连接对象与发送解耦

`Internalconnection` 保存 socket、读缓冲、发送队列、连接所属 Reactor、活跃时间与每连接窗口。连接对象内置 `send_function`，由 Reactor 注册时初始化；业务层调用 `send(data)` 即可，不需要知道 fd 或 Reactor。

### 5.2 任务与线程白板

任务对象携带 `shared_ptr<Internalconnection>`，业务 worker 执行前写入 TLS 白板，执行后清空。连接断开不影响正在执行的任务，`send` 会返回失败由业务收尾。

### 5.3 协程挂起与信箱

业务查询数据库时，`co_await query_db(sql, params)`：

- 协程挂起，业务线程立即归还；
- Awaiter 中的 `Box` 作为信箱随 DB 任务投递；
- DB worker 写入 `rows / err`；
- 恢复任务经 blockingqueue 回到业务池，业务 worker 再 resume 协程。

结果通过 `DBResult` 返回：

```text
ok       查询是否成功
cancelled是否被取消
err      错误描述
rows     完整多行多列结果（业务层自行取用）
```

### 5.4 背压与滑动窗口

背压目标是“不丢弃数据，让压力回到上游”：

```text
每连接窗口限制单连接在途消息
  → Handler 根据 fast/db 分类
  → db 任务必须领取 DB 准入额度
  → 额度不足进入等待区并暂停读取
  → divide / work / DB 使用有界队列
  → 队列高水位阻塞生产者，低水位唤醒并通知 Reactor 重试暂停连接
```

额度按业务流程持有：一次业务即使多次查库，也只在整条流程结束后释放额度。为此额度令牌随 divide 任务、work 任务、协程恢复任务逐段传递。

### 5.5 发送优化

- BatchSender 把同批待发送的 Reactor 合并为一次 eventfd 唤醒；
- Reactor 内把同一连接的多条封帧消息合成为一个 batch string 后一次 `write()`；
- 半截写与 `EAGAIN` 场景保留剩余数据并等待 `EPOLLOUT` 继续。

### 5.6 数据库参数化与动态结果读取

SQL 使用 prepared statement，`?` 占位参数按顺序绑定，杜绝字符串拼接注入。读取结果时列缓冲区按需扩容，长字段不会截断，循环读取直到 `MYSQL_NO_DATA`。

### 5.7 心跳

连接每次读写刷新 `last_active_us`，事件循环周期扫描，空闲超过 60 秒的连接自动清理。

### 5.8 指标与日志

各模块通过接口完成原子埋点，采样线程每秒聚合输出 QPS、平均延迟、P99、队列深度、连接数、CPU、RSS 等。日志使用队列 + 后台线程批量写文件，支持级别过滤与退出前 flush。

### 5.9 优雅退出

```text
停止 accept
  → 解析池排干
  → 业务池排干（DB 保持可用）
  → 结算挂起协程
  → 排空 BatchSender
  → 停 Reactor 并断开连接
  → 关闭连接名册
  → DB 最后关闭
  → 停指标线程、排空日志
```

## 6. 对外接口

### 6.1 集成入口

```cpp
Server server(divide_work, port, parse_threads, work_threads, reactor_count);
server.mark_fast_prefix("ping");
server.mark_db_prefix("hello");
server.set_db_config({ ... });
server.set_error_handler(...);
server.start();
```

### 6.2 业务接口

```cpp
send(data);                                   // 回复当前连接
framework_call(cmd, args);                    // 单发 / 组播 / 分组 / 关闭
co_await query_db(sql, params);               // 参数化查询
```

### 6.3 框架调用命令

| 命令 | 作用 |
|---|---|
| `bind` | 绑定业务虚拟连接标识与连接组 |
| `send_to_sb` | 按虚拟标识单发 |
| `send_to_gp` | 按连接组组播 |
| `divide_gp` | 重建连接组 |
| `set_group` | 调整单个连接的组 |
| `close_conn` | 主动关闭连接 |

## 7. 质量验证

压测环境：WSL / i7-12700H（20 逻辑线程）/ MariaDB / 本机回环。

| 场景 | 结果 |
|---|---:|
| v0.8 2000 连接 × 16 并发回归 | 约 1,492,192 请求，QPS 8,192，0 错误 |
| TSAN 2000 × 16 | 无 data race 报告 |
| 30 分钟混合长稳 | 约 1,700 万请求，0 错误，RSS 稳定 |
| 1 小时随机连接抖动 | 约 3,417 万请求，QPS 9,477 |
| 超载灌压 | 整体 QPS 27,505，峰值约 71k |

正确性上累计完成千万级请求，无串包、漏回、错序；稳定性上通过 TSAN 与长时间运行验证；吞吐受单机 CPU、数据库与压测客户端限制。

## 8. 可扩展方向

- 按业务类型拆分多个业务线程池，实现故障与负载隔离；
- 路由分类扩展为业务池路由；
- 接入 HTTP / protobuf / gRPC 等协议层；
- 在 DB 之外接入 Redis 等重 IO 模块，复用协程机制；
- 额度、路由等抽象为通用接口；
- 增加本地管理命令池与运维控制台；
- 多实例部署与网关横向扩展。
