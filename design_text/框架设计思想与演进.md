## 一、设计主线速览

这个框架不是先定一张大架构图再填充功能，而是每遇到一个真实约束就往前走一步：

```text
短任务模型（解析 → 调用功能 → 返回）
  → epoll 收消息 + 线程池执行
  → 拆网络层 / 解析池 / 业务池
  → Handler 解耦层间依赖
  → DB 要独立成池，业务线程不能阻塞
  → 协程挂起 + 阻塞队列恢复 + 信箱传数据
  → send function + 线程白板解决“当前连接是谁”
  → try/catch、错误回调、优雅退出补稳定性
  → 多 Reactor + eventfd + BatchSender 补性能
  → 指标 / 日志 / 参数化 SQL / 心跳补运维安全
  → connect_book + FrameworkCall 补通用服务
  → 上游放行非 DB、截流 DB 的背压方案
  → 额度随业务流程走、攒批发送、DB 动态读长结果
```

---

## 二、起点：为什么用 epoll + 线程池做短任务

学习 epoll 和线程池时注意到：一般的短任务实现就是“接收一段信息 → 解析 → 调用对应功能 → 返回结果”。这非常契合两种技术的特点：

- epoll 承担“接收外界调度信息”的职责；
- 线程池承担“解析并调用对应功能”的职责。

于是产生第一个原型目标：**用 epoll 拿到消息，把解析和执行交给线程池，框架只负责把这些环节接起来。**

出于解耦的考虑，一开始就希望网络层和线程池分开；同时想到并发业务场景时，感觉可以“多个线程池跑不同业务”。为了让后续扩展更方便，把解析单独拉成一个池子，于是有了：

```text
epoll / Reactor（收消息）
  → 解析线程池（消息 → 业务 function）
  → 业务工作线程池（执行 function）
```

这个拆分在当时是“为将来预留”：以后可以按业务类型再分多个业务池，而解析层只需要负责把消息翻译成可执行任务。

## 三、分层与 Handler：解耦不是口号

早期设想是各层各司其职，但实践时很快遇到一个问题：如果各层互相 include 头文件，改动一点就会牵连一片。

解决办法是引入 Handler 作为层与层之间的中间件，把依赖方向固定下来：

```text
网络层 Handler：收包后把消息交给解析层
解析层 Handler：把解析出的业务任务交给业务层
DB Handler：把查询任务交给数据库层
```

后来这套做法稳定成“接口 + make 实现 + 工厂”的模式：

```text
Handler_xxx.h             只声明该层应该提供什么能力
Handler_xxx_make.h/.cpp   真正持有下一层引用并接线
Factory                   由集成层统一创建
```

好处：上层只依赖接口，不依赖具体实现；以后替换某层内部实现，不需要改业务代码。

## 四、任务设计：每层任务只带它该知道的信息

解析线程池的任务应该携带：

- epoll / Reactor 传来的完整消息；
- 这条消息属于哪个连接。

业务线程池的任务应该携带：

- 解析后得到的可执行任务；
- 这个任务对应的连接。

发现 `std::function` 很适合解耦后，把“解析结果”固定为 function：

```text
解析池得到消息 → 调用业务入口 divide_work(msg)
divide_work 返回 std::function<void()>
业务池 worker 只负责执行这个 function
```

worker 不需要认识业务类、协议细节或具体命令，任务自带“该调用谁、怎么调”。

## 五、数据库、协程、阻塞队列与信箱

### 5.1 为什么引入协程

数据库不能直接内嵌在业务层：它应该像其他模块一样解耦出去，也就是要有自己的线程池。既然 DB 自己会跑，业务线程当然不应该阻塞在那里等结果。

所以需要一种能力：**把当前执行上下文保存下来并挂起，等 DB 完成后再把它唤醒继续跑。**

### 5.2 为什么不能用完成方直接 resume

初版很容易想到“DB 做完后直接 resume 协程”，但这样会带来两个问题：

- resume 会直接占用线程，等于在 DB 线程里继续跑业务；
- 业务协程在哪个线程被唤醒不可控，容易造成线程池语义紊乱、协程帧并发访问。

因此唤醒必须重新回到业务池：协程挂起时把“恢复任务”登记到阻塞队列，DB 完成后再执行唤醒函数，把恢复任务从阻塞队列取出、重新投回业务任务队列，由业务 worker 执行 `handle.resume()`。

```text
业务协程 co_await query_db(...)
  → 挂起
  → 把恢复任务放进 blockingqueue（按 wait_key 存放）
  → 把 DB 任务投给 DB 池
DB worker 执行 SQL
  → 写结果到信箱
  → 投一个“取回恢复任务”的唤醒任务给业务池
业务 worker 执行唤醒任务
  → 从 blockingqueue 取出 blockedtask
  → 把协程恢复任务重新入队
  → 真正 resume 协程
```

### 5.3 信箱机制：结果怎么回到正确的协程

跨线程传数据不能靠“找到发起线程”，所以采用信箱：

- Awaiter 里定义一个 `Box`（信箱）；
- 挂起时把信箱连同 DB 任务一起投给 DB 池；
- DB worker 把结果写进 `box.rows / box.err`；
- 唤醒后协程从 `box` 读取 `DBResult`。

信箱是一个“单消费者的公共空间”，唤醒信号本身不携带数据，只负责通知“去读信箱”。

## 六、业务接口：send function + 线程白板

### 6.1 为什么不把连接参数传给业务

业务层要发送消息，第一个直觉是提供“带连接参数”的函数。但这要求业务层知道具体连接、甚至知道 fd，对业务开发者负担太大，也破坏了隔离。

解决办法：连接结构 `Internalconnection` 里直接内置一个 `send_function`，由网络层在连接建立时初始化。

```text
业务调用 send(data)
  → 实际执行当前连接的 conn->send_function(data)
```

### 6.2 线程怎么知道“当前连接”是谁

function 解决的是“怎么发”，还没解决“给谁发”。查询到线程白板机制后，用 TLS 解决：

- worker 取出任务时，先把 `task.conn` 写进线程白板；
- 业务函数执行期间通过白板访问当前连接；
- 任务执行完清空白板。

白板是 `thread_local`，不是全局共享变量。协程恢复时恢复任务也携带连接，所以即使在另一个 worker 上恢复，白板也会被重新设置成正确连接。

最终把 `send()`、白板访问、`query_db()` 等封装成一个接口文件，业务层只需要 include 它，不接触框架内部结构。

## 七、稳定性：差错控制与优雅退出

### 7.1 错误处理

原型跑通后最明显的问题是“一碰就崩”：缺少 try/catch 时，任何异常都会带走整个进程。

因此：

- 每个池的 worker 对任务执行包 try/catch；
- 捕获后走 `ErrorHandler` 回调，让业务层决定如何记录 / 响应；
- 同时日志、指标并行记录。

异常从“进程级事故”变成“可观察的业务错误”。

### 7.2 优雅退出：不是关闸就完事

早期退出方式是直接关闭，容易造成在途数据丢失、任务被截断。

目标是：**关闸后放水，水流要按流程走完。**

```text
1. 关闭 accept 入口，不再接受新连接
2. 解析池关闸，等解析任务全部完成并投递
3. 业务池关闸，等业务任务排干
4. 结算仍挂起的协程（标记取消后重新投递，让业务自己收尾）
5. 排空 BatchSender，保证剩余发送写完
6. 停 Reactor，最后才断开全部连接
7. 关闭连接名册，唤醒可能等待版本变化的线程
8. DB 最后关闭
9. 停指标采样线程、排空日志
```

细节：各池中因条件变量等待的线程要靠 `notify_all` 唤醒；Reactor 的 epoll 等待则要靠 eventfd 唤醒。

## 八、性能演进：多 Reactor 与 BatchSender

### 8.1 为什么从单 epoll 走向多 Reactor

初版压测只到约一万 QPS。分析后认为单 epoll 事件循环成了瓶颈，因此把 epoll“分工”：

- `Acceptor` 只负责 accept；
- 新连接轮询分发给多个 `Reactor`；
- 每个 Reactor 持有自己的 epoll、eventfd 和事件线程。

连接信息里需要记录 `owner_reactor`，因为跨线程发送、主动关闭都要找到对应的 Reactor。

### 8.2 eventfd：Reactor 之间怎么唤醒

直接给 epoll 发系统信号会有惊群等问题。Reactor 采用和优雅退出唤醒一致的 eventfd 路线：

- 每个 Reactor 内置一个 eventfd；
- 需要唤醒它时向 eventfd 写入一个值；
- 事件循环被 eventfd 唤醒后处理待发送 / 待关闭 / 待恢复任务。

### 8.3 BatchSender：为什么发送要攒批

多 Reactor 后压测只提升约 50%，AI 分析认为系统调用次数是主要瓶颈：每条消息都唤醒一次、发一次。

发送的本质是 Reactor 遍历“待发送桶”。于是引入批处理模块：

```text
业务线程 send
  → 入队 + 标记对应 Reactor“有待发数据”
  → BatchSender 攒 Reactor 集合
  → 定时线程统一唤醒一次
  → Reactor 批量写出
```

近期进一步优化：同一连接待发队列里的多条已封帧消息会先合成一个 batch string，再一次 `write()`；半截写或 `EAGAIN` 时剩余部分插回队首，并注册 `EPOLLOUT` 等可写后继续。

## 九、运维与安全：指标、日志、参数化、心跳

### 9.1 指标系统

指标本质上是一个全局模块：

- 各模块完成任务后调用预埋点接口，内部只做原子计数；
- 独立快照线程按秒刷新并计算 QPS / 延迟 / P99 / 队列 / CPU / RSS；
- 输出提交给日志系统。

### 9.2 日志系统

设计与指标系统相似：

- 调用方只把格式化文本推进队列；
- 后台写线程批量写文件；
- 退出时 `flush_and_stop()` 保证日志不丢。

### 9.3 参数化 SQL

为防止 SQL 注入，DB 层使用 prepared statement：

```text
query_db("SELECT ... WHERE name = ?", { msg })
```

SQL 模板与参数分离，值永远以绑定参数传入。表名 / 列名不能参数化，需要业务层白名单校验。

### 9.4 心跳清理

为清理僵尸连接引入心跳机制：

- 连接每次有读写刷新 `last_active_us`；
- 事件循环原本定时醒来，顺带扫描空闲连接；
- 超过 60 秒没有活动的连接被清理。

连接刚注册时就必须初始化活跃时间，否则冷启动第一批连接会被误判超时。

## 十、通用服务：连接名册与框架调用

### 10.1 为什么需要连接名册

线程池 + 短任务的特殊性在于：worker 默认只能拿到自己正在执行的连接，很难给“其他连接”发消息。业务层还经常需要知道一组连接（群组、广播、主动关闭）。

因此引入连接名册：

- Reactor 建立连接 / 断开连接时调用 `on_connect / on_disconnect`；
- 名册记录“连接 → virtual_fd、连接组、版本号”；
- 存储用 weak_ptr，不拖长连接生命周期。

### 10.2 virtual_fd：为什么业务拿不到真实连接

解耦与隔离要求业务层不接触真实连接对象。于是提供一张“虚拟连接映射表”：

- 连接刚建立时先用 socket fd 作为临时 virtual_fd；
- 登录 / 鉴权成功后由业务调用 `bind`，换成业务虚拟标识；
- 业务调用时传 virtual_fd，框架内部再映射回真实连接执行 send / close。

### 10.3 FrameworkCall

框架调用层负责命令分发，内置：

```text
bind        绑定业务虚拟标识
send_to_sb  按 virtual_fd 单发
send_to_gp  按连接组组播
divide_gp   重建连接组
set_group   调整单个连接组
close_conn  主动关闭连接
```

一个关键设计判断：**框架调用不需要挂协程。** 因为挂起后也没有别的空闲线程池来接，最后还是要在当前业务池跑完，不如直接同步执行完。

真正需要挂起的场景仍可以复用 EventAwaiter，所以框架调用内部并非不能用协程，只是当前默认路径没必要。

### 10.4 框架外长连接线程

业务层若存在框架外独立运行的“长连接线程”（比如状态机、独立会话），它无法使用 worker 白板。为此提供 `ConnectionSession` 句柄，并让连接名册带版本号：

- 长连接线程持有会话句柄；
- 名册变化时版本号自增；
- 会话可用条件变量等待版本变化，不空转轮询。

### 10.5 还未落地的本地管理接口

作者原本设想加入本地管理接口：

- 内置一个本地命令解析池；
- 解析管理命令后调用 FrameworkCall 与各模块接口；
- 实现实时查看 / 控制系统。

这属于规划方向，尚未实现。

## 十一、背压：整个设计里最难的部分

### 11.1 约束与早期尝试

背压的朴素做法是“额度用完就丢”，但作者明确不接受丢数据。

学习背压原理后，方向是控制上游水量：

```text
下游队列到达额度 → 返回结果 → 上游阻塞
→ 再继续传递给更上游
```

这样不丢数据，逻辑也通畅，但落到协程 + DB 时变复杂：

- DB 有自己的背压队列；
- 如果积压，阻塞队列可能内存爆炸；
- 如果让线程阻塞，并发优势又丢了。

尝试“把协程帧打包丢回任务队列排队”，本质上只是再造一个队列，仍然可能积压，治标不治本。

### 11.2 关键洞察：该截流的是 DB，不该截流非 DB

最终想清楚一点：

```text
要保持高并发的其实是非 DB 任务；
DB 任务在本质上是只能等待的。
```

因此做法是：上游对业务做分类，放行非 DB，截流 DB。

### 11.3 为什么额度闸放在 epoll 与 divide 的交界

一开始想放在 divide_pool 内部，但那样额度不足会堵住解析池，连非 DB 也被拖住。

所以额度分配上移到**有内核缓冲区的 epoll 与 divide 之间**：

```text
非 DB 消息：直接投递，只受队列背压影响
DB 消息：必须先领取 DB 额度，才能进入 divide_pool
额度不足：消息进入 DB 等待区，暂停该连接继续读
```

配套组件：

```text
RouteClassifier      判断 fast / db
DB_credit_gate         DB 额度分配
DB_waiting_queue   DB 额度不足时的等待区
Reactor pause/resume 暂停和恢复连接读取
```

### 11.4 每连接窗口与等待区

为限制单连接在途量，引入 ConnectionFlow：

- 同一连接最多约 8 条在途消息；
- 在途量达到窗口后暂停读取（不触发新读事件）；
- 已读到但判定为 DB 且额度不足的消息，先塞进连接的等待区；
- 额度释放时再由 Reactor 唤醒补投。

### 11.5 业务层需要提供的信息

这套机制最大的设计成本是：**业务层的解析设计里必须能区分“这是不是 DB 任务”**，否则额度闸无法工作。当前用消息前缀声明 fast / db：

```text
server.mark_fast_prefix("ping");
server.mark_db_prefix("hello");
```

### 11.6 一次业务多次查库：额度释放位置修正

后来业务试用发现：一个业务流程里多次查库时，旧实现在“第一次 SQL 完成”就释放额度，等于额度只约束了第一段，后续查询不受控。

修正方式：

```text
释放点从 DB 池的“单次 SQL 完成”移到业务池的“整个业务流程结束”。
```

由于协程业务流程会被拆成多个 work_task / resume 任务，需要让额度信息跟着任务走：

- 网络层准入成功后创建 `DB_credit_token`；
- 令牌随 divide_task → work_task 传递；
- 协程挂起时 `await_suspend` 把当前令牌复制到恢复任务（线程白板承载）；
- worker 只有发现任务“执行完且不再挂起”时才归还令牌。

这样一次业务里多次 `co_await query_db` 只占一个额度，直到整个流程真正结束。

## 十二、近期性能与正确性修正

### 12.1 Reactor 攒批发送

旧实现中 Reactor 对同一个连接逐条读取队列消息并逐条 `write()`，系统调用偏多。

现在：

- `send_queue` 改为 `deque<string>`；
- `try_send` 把最多约 64KB 的已封帧消息合成一个 string，一次 `write()`；
- 写不完 / EAGAIN 时剩余部分插回队首，并注册 `EPOLLOUT` 等待可写；
- 全部发完后关闭 EPOLLOUT。

### 12.2 DB 结果动态扩容

旧实现为结果列固定绑定 256 字节缓冲，遇到长字段会截断并停止读取后续行。

现在：

- 先按 256 字节绑定；
- `mysql_stmt_fetch()` 返回 `MYSQL_DATA_TRUNCATED` 时，从 length 指针拿到实际长度；
- 只对该列扩容为 `实际长度 + 1`；
- 用 `mysql_stmt_fetch_column()` 取回完整数据；
- 循环以 `MYSQL_NO_DATA` 结束，长字段不会中断整张结果集。

### 12.3 v0.8 并发竞态修复

用 ThreadSanitizer 定位并修复三处生命周期问题：

- 指标采样器必须先注册完成，再启动采样线程；
- DB 不能在协程尚未真正挂起时提前 resume（引入 coroutine_suspend_guard）；
- `on_connect` 必须在连接对 Reactor 可见之前执行。

### 12.4 v0.9 第二阶段修正

- Acceptor 恢复为独立的 `epoll + eventfd`；
- `ConnectionFlow::release_slot()` 不再产生无人消费的 `resume_pending_`；
- divide 队列满时 Reactor 暂停单连接，低水位回调后重试；
- `take_one_message()` 支持非法前缀重同步，并限制读缓冲大小；
- 协程挂起屏障改为条件变量，不再依赖自旋超时；
- 发送队列增加字节上限，写成功也刷新心跳活跃时间。

## 十三、设计原则沉淀

- 短任务定位：请求进来 → 处理 → 返回，在业务池内完成；长任务由业务层独立线程承担；
- 业务层保持薄：只依赖 `context.h` 与 FrameworkCall，不接触 fd / epoll / Reactor；
- 层间只通过接口 / Handler 协作，方向固定；
- 该等线程的线程等，该协程等的协程等；完成方绝不直接 resume；
- 连接上下文随任务走，断线不杀在途任务；
- 不丢数据：背压最终表现为暂停上游 / 等待区，而不是丢弃；
- 关闸后放水：退出按层排干，DB 最后关闭；
- 每个机制都要回答“数据从哪来、回到哪去、由谁唤醒、谁负责清理”。

## 十五、作者的一句话总结

> 框架的成长基本是“功能跑通 → 压测暴露问题 → 稳定性补课 → 通用服务补位 → 背压把边界想清楚”的过程。它也许不是一个性能怪兽，但每个关键机制背后都有明确约束，这是它最值得保留的地方。
